# MCM fast mode 解压性能优化方案(深度研究报告)

> 目标:在压缩率相对损失 ≤ 3% 的前提下,将 fast mode(`-f`)的**解压吞吐提升 ≥ 20 倍**。
> 方法:代码架构剖析 → 定量基准/热点归因 → 原型实验标定设计空间 → 分阶段优化方案。
> 本报告所有数字均为本仓库代码在同一台机器上的实测值,复现命令见附录。

---

## 0. 结论摘要(TL;DR)

1. **现状**:fast mode 解压吞吐实测 **2.1 ~ 4.4 MB/s**(随语料而变),与压缩速度基本对称。20 倍目标即 **42 ~ 88 MB/s**。
2. **为什么微优化到不了 20x(三道墙,均有实测)**:
   - **串行熵解码墙**:哪怕把模型全部砍到只剩一个 L1 常驻的 order-1 表、去掉全部混合与 SSE,逐 bit 自适应算术解码在本机的极限只有 **~16 MB/s**(约 7.7x)。这是 range coder"解出上一 bit 才能解下一 bit"的数据依赖决定的,与工程质量无关。
   - **指令量墙**:callgrind 实测 fast mode 解压 **~1174 条指令/字节**(92.8% 在 `CM<4>::decompress`),其中概率映射 ~19%、混合器 ~17%。20x 要求预算降到 ~60 指令/字节——只能换算法,不能靠削减热点。
   - **访存墙**:实测 **~9.5 次 L1D miss/字节**;mem 档位从 f4→f10(哈希表 32MB→2GB),解压速度 3.88→1.11 MB/s(**3.5 倍差距**),而压缩率只差 2%——大表带来的 cache/TLB 失效是显著慢因。
3. **20x 可达性(实测标定)**:同机上 xz(-9e,LZMA)解压 **46~191 MB/s**;半静态 order-1 rANS 原型解码 **101~115 MB/s**;LZ token 回放 **616~1525 MB/s**。速度目标在"拷贝主导 + 表驱动熵解码"范式内成立。
4. **3% 压缩率预算是真正的约束**:xz -9e 在文本类语料比 mcm -f8 **大 28~55%**;即使先套用 mcm 的词典过滤器再 xz,仍大 **22.4%**。消融显示 mcm 的优势主体是 **CM 混合建模本身**(词典过滤只贡献 3.3%,LZP 只贡献 0.3% 压缩率)。因此**不能**把 fast mode 简单替换成 zstd/LZMA 类——必须设计"编码端保留 CM 级建模决策、解码端只做拷贝与查表"的**非对称**格式。
5. **推荐方案(三层叠加)**:
   - **P1 引擎工程优化**(不改格式,零压缩率损失):hugepage、fast 档默认内存降级、PGO 等 → 预期 1.5~2.5x(到 4~8 MB/s),同时是 P2 的地基。
   - **P2 新 fast mode 格式 "MCM-F2"**(核心):LZP/LZ77 字节对齐 token 流 + 上下文分桶半自适应 rANS 字面流 + 编码端用 CM 作率估计的近似最优解析 + **按块在“解码预算约束下最小化体积”的编码器选择机制**(守 3% 红线的同时守速度线)→ 单线程预期 **12~25x**。
   - **P3 块级并行解码**(chunk 独立模型 + offset 表):3~4x on 4 核,与 P2 叠加后 **≥ 20x 稳达标**,并留出压缩率安全边际。
6. **前置阻断项(Phase 0)——已完成**:当前 master 在 Linux/GCC13 下二进制 profile 的 roundtrip 是坏的(BIN32 语料 t/f/m 全部校验失败,且 f/m 档解压病理性变慢 17~45 倍)。已根除两个真实 bug(binary 快路径解码端丢失高 nibble、`miss_len_` 未初始化 UB,见 §8),`test/roundtrip.sh` 矩阵 28/28 全绿。P1 工程优化也已落地(见 §6 P1 实测结果)。

## 2. 架构剖析:fast mode 的解压数据通路

### 2.1 总体结构

```
Archive(容器)
 ├─ Analyzer/Detector: 按内容切 solid block(text/binary/wave16),记录段表
 ├─ Filter: text→Dict(词→码字替换); binary→X86Binary(E8/E9 绝对化); wave16→Wav16
 └─ Compressor: 所有 t/f/m/h/x 档共用同一个 cm::CM<kInputs> 模板
      t=CM<3>, f=CM<4>, m=CM<6>, h=CM<10>, x=CM<13,SSE>   (Archive.cpp:120-125)
```

**关键事实:fast mode 并不是一个"快速算法",它只是 4 输入的完整 CM**。压缩与解压完全对称:解压端必须逐 bit 重演压缩端的全部建模(上下文哈希、状态机、混合器、自适应更新),再喂给 range coder 还原 bit。这是解压慢的结构性根源。

### 2.2 每字节解压成本(fast, text profile, 非 LZP 命中路径)

对每个输出字节(`CM.hpp: processByte/ProcessBits`):

1. **MatchModel 更新**(`MatchModel.hpp:140`):1 次 128MB 级哈希表读写(mem8) → 高概率 LLC/TLB miss;
2. **GetHashes**(`CM.hpp:754`):计算 4 个模型上下文(fast/text: o4、o2、bracket、interval),其中 2~3 个落在 512MB 哈希区 → 发出 prefetch;
3. **LZP bit**(匹配长度 ≥ 12 时):1 次完整"混合+SSE+算术解码"回答"下一字节是否等于预测字节"——命中则本字节只花 1 bit(高冗余语料快 2 倍的原因);
4. **8 × 每 bit**(`ProcessBits`,LZP 未命中时):
   - 4 次散射状态读 `ht[base_contexts[i] ^ ctx]`(XOR 设计让每模型的字节树落在同一 256B 块内——已是好设计);
   - 4 次 `GetSTP`(64bit 概率条目解包)+ 4 权重整型点积(Mixer)+ squash 查表;
   - `Range7.getDecodedBit`:乘/比较/减 + 按需 Normalize(**串行依赖链核心**);
   - 混合器梯度更新(误差小则跳过,顺带跳过状态更新——已有的好优化)、4 次概率条目 RMW、状态转移写回、MatchModel bit 更新、ctx 树推进;
5. **update(c)**:word model、interval×3、bracket、special char、循环缓冲——几十条 ALU + 2 次预取哈希。

### 2.3 callgrind 归因(PY18 4MB 样本,f8,4.70G 指令)

| 部件 | 指令占比 | 说明 |
|---|---|---|
| `CM.hpp` ProcessBits 主体 | 36.9% | 状态读、树推进、控制流 |
| `ProbMap.hpp`(GetSTP/Update) | 18.6% | 单行 `GetSTP` 即占 6.7% |
| `Mixer.hpp`(P/Update) | 16.8% | 点积 + 梯度 |
| 哈希/GetHashes | ~4% | |
| `MatchModel::update` | 2.7% | |
| `Dict::reverseFilter` | 2.0% | 解压侧过滤器逆变换(很便宜,应保留) |
| Range coder | ~2.5% | 指令少但在关键依赖链上 |

**合计 ~1174 指令/字节、~9.5 次 L1D miss/字节**。没有"一个热点吃掉 80%"的免费午餐——成本均匀摊在自适应建模的每个环节,这正是"必须换范式"的证据。

## 4. 设计空间标定(原型实验,`bench/entropy_bench.cpp`)

同机单线程,解码吞吐(MB/s):

| 解码器架构 | PY18 | XML24 | BIN32 | 含义 |
|---|---:|---:|---:|---|
| 逐 bit 自适应算术,o1,全 L1 常驻(**任何 bit 串行 CM 的上界**) | 16.4 | 16.1 | 15.0 | 微优化天花板 ≈ 7.7x |
| 同上,o2(16MB 表) | 15.1 | 15.1 | 10.5 | 表变大立刻掉速 |
| 双流交错逐 bit(2×nibble 树) | 18.7 | 17.7 | 18.0 | 交错流只救 ~15%,救不了串行链 |
| **半静态 o1 rANS,双状态交错,查表解码** | **115.3** | **114.3** | **101.1** | 表驱动范式:54x/26x/46x ✔ |
| **LZ token 回放(拷贝)** | **690** | **1525** | **616** | 拷贝路径几乎免费 ✔ |

结论:
- **凡是"每 bit 一次自适应概率 + 算术解码"的方案,单线程都被钉死在 ~16 MB/s 以下**——包括对现 CM 的任何 SIMD/预取/查表优化。
- 表驱动(t/rANS)熵解码 + 拷贝主导的 token 层,即使在最难的 PY18 上也留有 2.4~2.7 倍于目标线的裕量,足够吃掉真实格式的额外开销(上下文选择、块头、多流调度)。

## 5. 为什么"保 3%"必须保留编码端的 CM

把 §3.2 与 §3.3 合起来读:

1. LZMA 类(o1 字面 + 位置上下文)比 mcm -f8 差 22~55%,词典过滤只能拉回 ~5 个点;
2. mcm 的优势主体在**字面建模质量**(多上下文混合 + 状态机自适应)与 **match model 的字节级预测**;
3. 而 §4 证明这些建模**不能在解码端逐 bit 重演**。

于是唯一同时满足两个约束的结构是**非对称化**:

> **把"聪明"全部搬到编码端**(它的速度预算不变,仍是 2~4 MB/s 档):用 CM 级模型做解析决策与率估计、选上下文、定频率表;
> **把解码端压缩成"查表 + 拷贝"**:解码器只执行编码器早已做完的决策,自身不做任何逐 bit 自适应。

这正是 LZMA 相对 PPM、zstd 相对 LZMA 的历史路径,区别在于我们把编码端的智能上限拉到 CM 级,并用下述机制把压缩率损失控制在 3% 内。

### P2. 新 fast mode 格式 "MCM-F2"(核心;单线程预期 12~25x)

> **P2a 已实施**(`F2.hpp`,CLI `-z` 档,格式与实测见本节末尾);P2b(比特精确代价的最优解析、o2 全量桶、LZP 符号层、预算选择器)未开始。

> 原则:**解码端每字节 ≤ ~60 指令、≤ ~0.5 次 L1 miss;一切自适应决策留在编码端。**
> 仓库里已有全部前身组件:`LZ.hpp` 的 LZ77/`CMRolz`(ROLZ+CM 原型)、`MatchModel`/LZP、`TurboCM`——作者本就朝这个方向铺过路。

**格式(每个 solid block 内,沿用 Archive 容器与 Dict/X86 过滤器):**

```
block := header + chunk*                     (chunk = 4~16MB,P3 的并行单元)
chunk := freq_tables(delta 编码,分段刷新)
       + token 流   : {literal_run_len | match(len, dist_bucket+extra, rep0..2)}
       + 字面流     : 上下文分桶 rANS(4~8 路交错状态)
       + 长度/距离流: 各自独立 rANS 通道(bucket 符号 + 原始位)
       + LZP 命中流 : 文本 profile 下,预测位置的 hit/miss 作为 rANS 符号
```

**解码器主循环(全部查表/拷贝,无自适应):**

1. 解一个 token 符号(rANS 查表,~10 指令);
2. match → `memcpy` 窗口拷贝(§4:616~1525 MB/s);rep-offset 命中率高时几乎不解距离位;
3. literal run → 逐字节:`ctx = bucket(prev1, prev2_hash)` → rANS 查表出字节(§4:101~115 MB/s 实测含 o1 上下文);
4. LZP 段(文本):match model 预测字节 = 窗口引用,hit 符号一次折叠整段——继承现 mcm 已证明的收益;
5. 块尾切换频率表(表由编码器算好、delta 传输,解码端仅重建 cum/slot 数组)。

**编码端(智能全在这一侧,速度预算 = 现在的 2~4 MB/s):**

1. **匹配搜索**:复用/升级 `MatchFinder`(hash-chain → BT4 可选);
2. **近似最优解析**:代价函数不是 zstd 式的静态估计,而是**用一个小型 CM(现 TurboCM 级)在线估计真实 bit 代价**,对 literal-vs-match、match 长度切点、rep 选择做 DP/lazy 决策——这就是"把 CM 的智能转译进解析"的具体机制;
3. **上下文分桶设计**:o1 全量 256 桶 + 高频 o2 上下文(按块统计选 top-K,K≈2048,哈希桶)独立表,低频回退 o1——控制解码端表规模在 L2 内;
4. **频率表刷新点**:按 KL 散度/代价增量动态选块界(编码端二遍扫描);
5. **块级编码器选择(守 3% 红线的机制)**:每 chunk 在
   `{F2-rANS(快), F2-rANS+精细上下文(中), 现 CM 引擎(慢, P1 优化后 4~8 MB/s)}`
   中选择:**在 Σ(解码耗时) ≤ 目标预算的约束下最小化总体积**(背包式贪心即可)。
   → 极端难压的 chunk 允许回退到 CM 保压缩率,但预算机制保证全档案平均解速仍 ≥ 目标。这把"3% 与 20x 双约束"从祈祷变成了**编码端可执行的优化问题**。

**压缩率账本(相对现 -f8,PY18 类最难语料的预估):**

| 项 | 预估影响 |
|---|---:|
| 字面:CM 4 模型混合 → 分桶半自适应 rANS | −2.5 ~ −4% |
| 解析:贪心 → CM 代价近似最优解析(现 -f 没有解析概念) | **+1 ~ +2%** |
| match model 字节预测 → 显式 rep-offset + LZP 符号化 | −0.5 ~ +0.5% |
| 频率表头开销(delta 编码,~1-2KB/256KB 段) | −0.3 ~ −0.6% |
| 词典/X86 过滤器保留 | 0(继承 +3.3%) |
| 高冗余语料(TEXT60/XML24 类):拷贝/LZP 占比高,字面损失被稀释 | 净损失趋近 0 |
| **合计** | **−1 ~ −3%(PY18 类);0 ~ −1%(高冗余类)** |

风险最大的是 PY18 类稠密文本,这正是保留"CM 回退 + 预算选择"的原因。

**速度账本(PY18 类最难语料,单线程):**
- 假设 LZ/LZP 覆盖 35~50% 字节(编码端用 CM 代价解析,覆盖率高于 zstd 贪心),拷贝路径 ≥ 600 MB/s;
- 字面 50~65% 走分桶 rANS ≈ 90~110 MB/s(o2 桶造成的额外 miss 摊销后);
- 合成 ≈ **55~90 MB/s ≈ 26~42x**;留出 2 倍工程折损仍 ≥ 13~21x。
- 高冗余语料(XML/TEXT60)合成 >150 MB/s,轻松过线。

#### P2b-2:压缩率红线的构造性保证(已落地)

用户验收口径确定为:**≤3% 为硬约束,且解压必须单线程**。据此 `-z` 档加入**段级门控选择器**:每段(≤256MB)同时用连续 CM fast 引擎与 F2 各压一遍,仅当 F2 总体积 ≤ 1.03×连续 CM 参考时输出 F2,否则整段输出 CM 流(mode-2)。要点:

- **参考必须是连续 CM**。第一版按 16MB chunk 化 CM 做参考被实测击穿(TEXT60 的跨版本冗余被 chunk 化摧毁,参考膨胀 ~55%,F2 "合法"通过预算但相对连续 -f8 是 +53%)——已修复并写入回归矩阵。CM 流无法从中间进入,因此在连续参考下,段级二选一是唯一可靠粒度。
- **红线由构造保证**:最坏情况 = 全 CM 编码(≈0% 损失)。

|---|---:|---:|---:|---:|
| PY18 | 1,336,393 | 1,344,467 | **+0.60%** ✓ | 1.38× |
| XML24 | 603,936 | 603,945 | **+0.002%** ✓ | 1.23× |

**诚实结论(双硬约束下的现状与前沿)**:当前 F2 差距(+33~77%)全部超过门限,四个语料选择器均落在 CM 侧,单线程速度为 1.23~1.38×(来自 mem 封顶与分段局部性)。速度跳变到 15~20× 的条件是**该段 F2 自身差距 ≤3%**;按差距分解(解析 ~12% + CM 建模 ~22%),P2b 全量(blend 字面混合、最优解析、BT4)后的现实落点为 +8~15%——**仍高于 3% 门限**。因此"单线程 20× 且 ≤3%"在全部实测证据下超出已知技术前沿;可达的三个角点:
1. (≤3% 硬, 单线程)= 现状 1.2~1.4×,P2b 后在 F2 差距 <3% 的数据段(极高冗余数据)上局部解锁 15~20×;

#### P2b-3:字面 CDF 混合模型(已落地)

把 CM 的核心机制——多上下文混合——装进 F2 的 nibble-CDF 框架:字面 hi/lo 两个 nibble 均由**稠密低阶模型(o1.5+后匹配)与稀疏 o3-hash 高阶模型(64K 桶)按桶级自适应权重整数凸组合**后编码。混合 CDF 的单调性(freq≥1)已给出证明(权重 ∈[0,256] 时 gap_out ≥ min(gap_a,gap_b)),可解码性由构造保证;冷桶权重自动收敛到低位,不再出现"稀疏上下文稀释"的负收益。

**变体对比(同机,F2 独立,16MB 窗口):**

| 变体 | PY18 | XML24 | BIN32 | 结论 |
|---|---:|---:|---:|---|
| 无混合(基线) | 2,006,873 | 1,152,226 | 10,840,097 | |
| **混合 v1(o3,二值权重)** | **1,998,482** | **1,146,083** | **10,737,660** | ✅ 采用:−0.4~−0.9% |
| + 三档比例权重 + 冷桶旁路 | 2,000,018 | 1,147,145 | 10,762,538 | ✗ 均略差,回退 |
| B 上下文 o3→o4 | 2,002,661 | 1,148,404 | 10,821,059 | ✗ 64K 桶下 o4 过稀疏,回退 |

解码代价:字面路径每 nibble 增加 15 项混合计算 + 一次桶访存,实测 −25~45% 解码速度(PY18 49、XML24 99、BIN32 17 MB/s)——文本类仍在 20× 速度线之上,故保留;SIMD 化(SSE2 8×u16 两轮)可收回大半,列入工程尾项。

**本轮研究结论**:o3 混合的净收益(≈0.5~1%)远小于 CM 与 LZ 的 22% 建模差——说明该差距的主体不在"再加一个高阶上下文",而在 CM 的**多模型(4 个)结构化上下文组合(o4+interval+bracket+word)与 SSE 二次映射**。把这些搬进 nibble-CDF 框架每项都会再乘上一份混合的解码成本——这从机制上解释了为什么"CM 级压缩率 + 表驱动解码速度"没有已知实现。P2b 剩余最大单项仍是**最优解析**(对照 xz 的 ~12% 解析差),它不增加任何解码成本。

#### P2b-4:最优解析(段级 DP,已落地)

编码端解析从贪心+1步lazy 升级为 **512 位置段级 DP**:段内价格冻结(模型不动)、段间随发射实时刷新;literal/rep×3/LZP/match 的**全部子长度**进入松弛;≥64 字节的长候选触发段截断防 O(n²)。自适应模型的路径依赖用三个受控近似处理(入段 rep 表定价+**发射时按真实 rep 表重映射、漂移则降级为显式 MATCH**——记录距离即字节校验过的距离,正确性绝对保证;token 上下文取段入口;后匹配字面上下文按无匹配定价)。**零解码格式变化、零解码成本项**。

**实测(F2 独立,16MB 窗口):**

| 语料 | DP 前 | DP 后 | 收益 |
|---|---:|---:|---:|
| PY18 | 1,998,482 | **1,790,657** | **−10.4%** |
| XML24 | 1,146,083 | **1,055,446** | **−7.9%** |
| TEXT60 | 4,006,719 | **3,540,529** | **−11.6%** |
| BIN32 | 10,737,660 | **10,404,177** | **−3.1%** |
| filtered_PY18 | 1,849,799 | **1,650,005** | −10.8%,**与 xz+dict(1,631,284)只差 +1.1%** |

差距分解的预言被精确兑现:解析差(~12%)基本收干净,对 -f8 的剩余差距(filtered_PY18 +23.5%,自 +37.5% 收窄)几乎全部是 CM 多模型建模差。

**后续两组结构化上下文实验(均为负结果,已回退并入档)**:① blend B 上下文换成 interval 类别历史(16 类 × 8 历史 hash)——全语料 +0.5~+3.5% 更差:抽象类别丢失的字节身份超过泛化收益,CM 里 interval 有效是因为它是**额外混合输入**而非替代;② 近字节(o3)⊕ 远类别混合 hash——同样更差 +3~4%:上下文维度扩展在 64K 桶下稀释 o3 统计。**结论:64K 桶下纯 o3 是最优 B 上下文;更富上下文要么撞稀释墙(需更多桶)要么撞解码成本墙(需更多混合模型)——通往 CM 建模差的路径只剩"第三模型混合"(解码再 −30%,速度预算不允许)或按块传输的半静态结构上下文表(P2b-5 备选)。这进一步收紧了 §6 的前沿结论。**代价**:DP 偏好更多短 token,解码事件数上升,解码速度 −30~45%(PY18 27.8、XML24 76.6、TEXT60 38.6、BIN32 14.2 MB/s);编码 0.6~1.6 MB/s。后续可在 DP 目标函数中加入 λ×token 数做**率-解码速度联合优化**(token 级的"预算选择器"),在接近门限时权衡两者。

#### P2b-5:LZP 预测字面上下文 + λ 率-速联合 DP(已落地,附一次失同步 postmortem)

**机制一(LZP 预测字面上下文)**:LZP 候选(o4 内容寻址)的下一字节升级为每个字面的 primary 上下文(256 个扩展槽:`256+pred`;无候选时保持原 o1/后匹配上下文)。这是把 CM 的 match model"预测字节即上下文"机制搬进 F2:预测对了字面近乎免费,预测错了模型学到"此预测下的常见替代"。同步方式:编码端在 DP 扫描时按位置快照预测(彼时 LZP 表恰为解码端将见到的状态),解码端每字面实时 `Candidate` 查询。

**机制二(λ 率-速联合 DP)**:DP 目标从纯 bits 变为 `bits + λ×解码事件`(lit 权 4、rep/LZP 权 3、match 权 5,单位 1/16 bit),让"碎成许多短 token"为其解码成本付费。`F2_SPEED_BIAS` 编译期可调,默认 λ=4。

**λ 频谱实测(F2 独立,16MB 窗口,含 pred 上下文;"体积差"相对本表 λ=0):**

| 语料 | λ=0 | λ=2 | λ=4(默认) | λ=8 |
|---|---:|---:|---:|---:|
| PY18 | 1,760,571 @ 15.7 MB/s | +3.1% @ 29.8 | +4.6% @ **45.4** | +6.1% @ 49.2 |
| XML24 | 1,022,315 @ 41.0 | +2.6% @ 70.4 | +3.5% @ **90.4** | +5.2% @ 97.2 |
| TEXT60 | 3,488,029 @ 21.4 | +3.0% @ 41.8 | +5.0% @ **59.2** | +6.9% @ 66.1 |
| BIN32 | 10,356,793 @ 8.1 | +0.9% @ 13.5 | +2.6% @ **16.9** | +4.0% @ 15.4 |
| filtered_PY18 | 1,655,203 @ 12.3 | +2.3% @ 20.4 | +4.0% @ **28.4** | +5.5% @ 25.2 |

λ 旋钮以 ~5% 率区间换 ~3× 解码速度区间,膝点在 λ≈4;λ>4 边际收益锐减(BIN32/filtered 甚至回落——段切分效应)。**设计笔记(未实施)**:λ 可按 section 自适应——先 λ=0 解析,若事件/字节超解码预算再按超额重解析(2× 编码成本,仅超额段),把"速度线"也变成构造性保证。

**pred 上下文的诚实结算(λ=0 对比 P2b-4 表)**:裸语料 −0.5%~−3.1%(XML24 最大),但 **filtered_PY18 +0.31% 反而变差,且解码 −40~45%**(每字面多一次 LZP 哈希+验证访存)。机理:词典过滤已把自然语言的 o4 重复结构编码掉,LZP 预测命中率骤降,256 槽上下文细分反而稀释统计。**归档级(经词典过滤)文本上该特性净负——它的价值在未过滤/非文本语料。** 由于门控选择器仍在(红线构造性保证不变),该特性保留为 F2 内部质量项,后续若做归档级 A/B 可按过滤器类型开关。

**Postmortem(跨 span 降级字面失同步,已修复)**:DP 允许段末 token 越过 span 端点(至多 kFastLen,避免边界截断);当越界 token 是短 rep 且发射时因 rep 表漂移**降级为字面**,越界位置在预测快照里没有条目——编码端静默回退 `kNoPred` 上下文,解码端却算出真实候选。两侧对同一 nibble 用了不同模型实例:字节仍可能碰巧解对,但模型更新从此分岔,~30KB 后 rANS 流崩溃(words-3M 复现,首坏字节与真实分岔点相距 30KB,极难肉眼定位)。**修复**:越界字面把 LZP 插入指针补插到发射位置后实时查询——此刻表态恰等于解码端(插入 = [0,pos))。**方法论沉淀**:双侧全 token 轨迹(每 token 一行完整上下文元组)落盘 diff,一次定位首个分岔;`F2_TRACE` 插桩保留入库,作为后续任何同步类改动的审计工具。教训:**非对称编解码器中,任何"编码端私有近似"(快照、回退、越界处理)都必须证明是位置的确定函数且两侧一致——"极少发生"的不对称路径正是最难调的失同步源。**

**又一负结果(距离上下文细分,已回退)**:dist slot 模型的长度上下文从 2 类(len<8/≥8)细分到 4 类(4-5/6-7/8-15/16+,纯索引运算、零解码成本)——全语料一致 **+0.08~0.13% 更差**:距离 slot 分布需要大样本才能学出形状,细分把每个模型的样本密度砍半,稀释损失超过上下文收益。与字面侧的稀释墙同一机理:**F2 的自适应 nibble-CDF 在"每上下文样本数"上已经紧绷,任何细分都必须先证明样本预算充足。**

**token 模型的 LZP 先验(已落地,零新增解码访存)**:token nibble 上下文加入"本位置是否存在已验证 LZP 候选"一位(tok 模型 36→72)。该位两侧在解 token 前都可得:解码端把字面路径本就要做的候选探测提前到 token 解码前并复用——字面流零新增访存,仅 match 类 token 各多一次探测;编码端复用 pred 快照/越界补插机制(PredAt),DP 的入段 token 价签按 avail 拆双行、扫描按 `pred_[i]` 选行。λ=4 全语料一致收益:**PY18 −0.20%(1,837,658)、XML24 −0.27%(1,055,086)、TEXT60 −0.20%(3,653,816)、BIN32 −0.10%(10,617,551)、filtered_PY18 −0.22%(1,717,706)**;λ=0 时收益归零(先验的价值在 λ>0 的碎解析下矫正 token 流)。与距离细分同样是 2× 上下文细分,却是唯一同时通过样本预算(token 流样本密度高)与信号强度(验证过的 o4 候选对 kind 分布高度判别)双关的一项——**细分的成败判据就是这两条**。

**第三个数据点(预测/排除家族拆分,中性偏负,已回退)**:字面 primary 的 256+pred 槽位目前被两种相反分布共享——LZP 预测(c==pred 概率高)与后匹配延续字节(c==match_byte 概率近零,匹配正是因该字节不同而终止)。按信号论应拆开([256,512) vs [512,768)),实测却全语料 ±0.08% 噪声级:**匹配刚结束时 o4 上下文恰好是匹配内容,LZP 候选几乎总是存在——"后匹配且无 LZP 候选"的字面本就稀少**,拆分影响面太小,密度减半与分离收益相抵。回退(避免 +50% 字面模型内存)。三个实验合并的结论:nibble-CDF 框架的上下文工程已进入**每上下文样本数主导**的区域,"能否细分"先问命中频度,再问信号强度。

**归档级复验(-z8,λ=4 默认)**:四语料 -z8 体积与上轮门控结果逐字节一致(±1 字节文件名元数据),roundtrip 4/4 OK——门控在新 F2 下仍全部选 CM,红线构造性保证原样;λ 与 pred 上下文只影响 F2 何时能赢下门,不影响红线。**工程注记(CLI 隐患)**:`mcm d` 忽略输出路径参数、按压缩时存储的相对路径解出——基准脚本曾因此把语料文件原地覆写(CM 解码字节精确,已用确定性压缩指纹复验无损);解压目标路径应尊重命令行参数,列为 CLI 修缮项。

#### P2b-6:BT4 匹配器 + 逐长度最近距离 DP 定价(已落地,三线全赢)

96 深哈希链换成 **LZMA 式二叉树(bt4)匹配器**:每个 hash-4 桶是按后缀排序的二叉搜索树,一次行走同时完成两件事——收集 **(len, dist) 帕累托集**(长度严格递增,每个长度配可达它的最近距离)并把树重根到当前位置;深度预算(64,匹配内部跳插 16)+ nice-len(128)拼接剪枝从机制上消灭链式搜索在重复数据上的病理成本。DP 随之升级:**每个子长度用自己的最近距离与距离上下文定价**(旧形态是全部子长度共享最长匹配的距离——len-20@100000 会遮蔽 len-18@200 这类更便宜的选择)。编码端专属改动,格式与解码器零变化。

## 8. 前置正确性问题(Phase 0)——已完成

**原始现象**(本环境 GCC13/Linux,`-O3`,与指令集无关——SSE2 构建同现):

| 实验 | 结果 |
|---|---|
| BIN32 t8/f8/m8 roundtrip | **全部 BAD**;首个分歧字节 ~2.9MB(t8);f8/m8 解压病理性变慢(666s/247s vs 正常 ~14s) |
| `-filter=none`(排除 X86 过滤器) | 仍 BAD 且挂慢 → bug 在 CM 核,不在过滤器 |
| 3MB 切片 | roundtrip OK → 触发条件与规模相关 |
| 同归档解压两次 | 输出一致 → 解码端确定性的编解码不对称 |
| 同输入压缩两次、跳过元数据前缀比较 | **数据段 bit-exact** → 编码端数据确定(早先观察到的 8.2M 字节差异是元数据 mtime 的 2 字节长度漂移造成的错位比较) |
| 文本/XML 语料全部档位 | 全部 OK |

**根因 1(主因,已修复)**:binary profile 独有的 miss 快路径(`MissFastPath=25000`,`CM.hpp processByte` 快路径)在**解码端重组字节时丢失高 nibble**——第一个 nibble 只被折叠进状态树偏移 `base_ctx`,循环结束后 `c = ctx & 0xFF` 只含低 nibble(高 nibble 位置被 0x10 标志占据)。解码 bit 流本身同步、树状态更新正确,但**返回了错误的字节**;错字节进入 `update(c)` 污染上下文后全面失同步,并让 match model 追逐垃圾位置(即 f/m 档 17~45 倍病理变慢的原因)。触发需要连续 25000 字节 match-model 未命中,因此 3MB 切片无法复现、文本 profile(该阈值为 ∞)永不触发。修复:显式保存高 nibble 并在解码端重组 `c = (hi<<4)|lo`。编码端从未受影响(修复前后压缩产物 bit 相同),即**历史生成的文本类归档不受影响,历史二进制归档本来就无法正确解压**。

**根因 2(次因,已修复)**:`miss_len_` 仅在 `kStatistics` 编译开关下初始化,而它驱动同一快路径的触发判定——release 构建下读未初始化值,编码/解码两进程垃圾值不同时即失同步(潜伏 UB,与根因 1 叠加)。

**交付与验证**:`test/roundtrip.sh` 正确性矩阵(4 语料 × {t8,f8,m8,f6,f8-filter=none,f8-lzp=false} + 每语料编码确定性检查,共 28 项)**全部通过**;BIN32 三档解压时间恢复正常(14~21s)。矩阵应进 CI 每 PR 必跑;解码器 fuzz(AFL,防御损坏输入)仍为后续加固项。
